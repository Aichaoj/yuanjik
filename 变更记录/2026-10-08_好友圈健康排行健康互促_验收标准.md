## 一、意图

给「AI数显 · 元健康」加上**轻社交三件套**，让用户之间能互相看见、互相带动、互相加油，形成留存与自然传播。

## 二、合规红线（**先看这段，它决定了三个功能的形态**）

| 红线 | 落实方式 |
|---|---|
| 健康数据属**敏感个人信息**，向他人展示必须**逐项单独同意** | 三个开关 `share_index` / `share_streak` / `in_ranking` **默认全关**；每一项独立勾选、可随时关闭并即时生效 |
| 不得暴露可识别身份与原始健康数据 | 只展示**昵称**（默认「用户+4位随机」，用户可改）与**指数分档/分数**；**绝不**展示生辰、体征、通道明细、病历 |
| 不得做疾病/诊疗表述 | 加油文案只用**中性作息模板**（如「今天也照顾好自己」），全部过合规护栏；排行不出现任何身体部位/疾病词 |
| 未成年人与骚扰防护 | 每人每日加油上限 3 次；可解除好友；解除后双方**立刻**互不可见 |
| 不做全区排行 | 排行**仅在本人好友圈内**，避免大范围健康数据比对与攀比风险 |

## 三、接口契约（新增，均需鉴权；不改既有字段）

```
GET    /api/v1/me/invite_code           → {invite_code:"8位大写字母数字", nickname}
POST   /api/v1/me/nickname  {nickname}  → 昵称（2-12 字，去敏感词）
GET    /api/v1/friends                  → {friends:[{friend_id,nickname,status,share_index,share_streak,in_ranking,score,streak_days,last_active}]}
POST   /api/v1/friends/invite {invite_code}          → 发起添加（status=pending，需对方确认）
POST   /api/v1/friends/accept {friend_id}            → 确认（status=accepted）
POST   /api/v1/friends/reject {friend_id}            → 拒绝
DELETE /api/v1/friends/{friend_id}                   → 解除（双向移除）
POST   /api/v1/friends/privacy {share_index,share_streak,in_ranking}  → 逐项开关（未传的项保持不变）
GET    /api/v1/friends/feed?cursor=&limit=           → 动态流（仅 accepted 且对本人已授权项）
GET    /api/v1/friends/ranking                       → 圈内排行（仅 in_ranking=true 的 accepted 好友 + 本人）
GET    /api/v1/friends/cheer/templates               → 中性加油模板（≥6 条，全部过护栏）
POST   /api/v1/friends/cheer {friend_id,template_id} → 送加油（每日上限 3 次）
```

**可见性规则（唯一口径，前后端必须一致）**：
- `accepted` 关系才可见；`pending` 双方互不可见分数与动态
- `feed` 中：分数仅当**对方** `share_index=true`；连续天数仅当对方 `share_streak=true`
- `ranking` 中：仅列出 `in_ranking=true` 的 accepted 好友与本人（本人未开启则自己也不上榜，但接口仍返回自己的名次提示为 `null`）
- 三开关只影响**别人看我**；关闭后**下一次请求即生效**（不做缓存，或缓存 ≤10 秒）

## 四、验收标准（可验证，逐条自检）

| # | 验收标准 |
|---|---|
| 1 | 新用户 `GET /friends` 为空；`ranking` 不含自己（三开关默认全关） |
| 2 | A 用 B 的邀请码发起 → `status=pending`；**此时 A 的 feed/ranking 都不含 B**（B 未确认） |
| 3 | B `accept` 后：双方 `GET /friends` 互为 `accepted` |
| 4 | 双方都开 `in_ranking` 后，`ranking` 含双方，且**按 score 降序**；未开启者不出现 |
| 5 | B 开 `share_index` 后，A 的 feed 中 B 那条**出现分数**；B 关闭后，**下一次请求即看不到** |
| 6 | `streak` 同理（`share_streak` 控制） |
| 7 | 同一好友第 4 次 `cheer` 被拒（`code` 为可读业务码 + HTTP 4xx），前 3 次成功 |
| 8 | 全部 cheer 模板通过合规护栏（无诊疗/疾病词）——用护栏函数扫描并断言 0 命中 |
| 9 | A `DELETE /friends/{b}` 后：双方 `GET /friends`、feed、ranking 均不再出现对方 |
| 10 | 昵称去敏感词；`invite_code` 8 位且唯一（并发创建 50 个不重复） |
| 11 | 前端：首页有「好友圈」入口；三区块（动态/排行/互促）可见；开关默认关；关闭后立即刷新可见性；430×932 无横向滚动、无 JS 报错 |
| 12 | 既有测试与既有接口零回归（内核 335 / 服务端 104；`daily`、`index`、`personalized` 字段不变） |

## 五、数据（新增 sqlite 表，沿用 `state.db`）

```
social_profile(member_id PK, nickname, invite_code UNIQUE, created_at)
social_privacy(member_id PK, share_index, share_streak, in_ranking, updated_at)
social_friend(id PK, a_member, b_member, status, requested_by, created_at, accepted_at, UNIQUE(a_member,b_member))
social_cheer(id PK, from_member, to_member, template_id, on_date, created_at)   -- 每日限额按 on_date 计
```
- 不存手机号/真名/生辰；`member_id` 已是账号派生 ID
- 解除好友 = 删除该行；不保留历史（合规最小化）
