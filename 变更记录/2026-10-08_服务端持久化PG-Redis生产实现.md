## 一、意图（要做什么）

把 `服务端` 的**内存版持久化**换成**PostgreSQL + Redis 的生产实现**，且**不改动任何既有接口契约**：

> 只做「新增实现 + 可注入切换」。接口签名、错误码、响应形状一律不动。

三处目标：`BaselineRepo`（PG）、`SessionStore`（Redis）、`IdempotencyStore`（Redis）。

**明确不做**：任何加密/抗量子/密钥管理实现（属关联方边界）；Redis 里只存不透明随机串。

## 五、本轮抓出的两个真实缺陷（由测试暴露，已修）

| # | 缺陷 | 暴露方式 | 教训 |
|---|---|---|---|
| 1 | `active_of()` 用无序 Redis SET 存 access token，而 Windows 上 `time.time()` 分辨率约 **15.6 ms**，连续登录的会话 `issued_at` 完全相同 → 排序不稳定，**"踢最早设备"会踢错设备** | `test_device_limit_kicks_oldest` 断言设备顺序时失败（得到 `dev-2, dev-1, …`） | 依赖"时间戳可区分先后"的逻辑，必须自带**确定性次序**；改为插入序 LIST |
| 2 | `sess:access:*` 若按 15 分钟 TTL 自然消失，过期令牌会被判为"未知令牌"返回 **20000** 而非 **20001**，**错误码形状被改变** | 写实现时对照 `AuthService.authenticate()` 的判定顺序发现 | 存储 TTL 的选择会**外溢成接口语义**；TTL 必须服从错误码契约，而非"看起来更省空间" |

## 六、如实声明：未验证项

1. **本机未安装 redis-server**：Redis 适配层的全部测试与验证跑在 `fakeredis 2.39.0` 上，**真实 Redis 实例未验证**。
   缓解：键布局与命令均按 redis-py 语义书写；设 `TYH_REDIS_URL` 后重跑 `_verify_pg_redis.py` 会自动切换到真实实例（脚本已内置该分支）。
2. **未做并发压测**：仅一条 6 线程同日并发写基线的用例；未做 QPS / 连接池饱和 / 长时间稳定性测试。
3. **环境变量在生产如何注入未在本机验证**：`TYH_PG_DSN` / `TYH_REDIS_URL` 的 vault→环境注入链路未跑。
4. **无多实例高可用**：连接池会丢弃坏连接并重建，但没有重试/熔断；Redis 未使用 Sentinel/Cluster。
5. **`rhythm.baseline.s_ref` 精度**：库列为 `numeric(7,4)`，比服务层的 6 位小数少 2 位（见 README §8.3 第 4 条，仅建议、未改 schema）。
