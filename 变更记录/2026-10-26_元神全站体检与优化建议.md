## 三、发现清单（按优先级）

### P1-1 签到后按钮永远显示「今日签到」，且仍可点 —— 根因已定位

**现象**（实测，账号 13093014205）：
- 点「今日签到」→ `POST /checkin` 返回 200、`observation_count 0→1`，顶部出现「连续记录 1 天」；
- 但按钮文案**始终是「今日签到」**、`disabled=false`，没有「今日已签到」，也没有 toast。
- `localStorage` 里出现 `yh.checked.true=1`，**没有** `yh.checked.2026-10-26`。

**根因**（`shuzi\web\app.js`）：
```js
var K_CHECKED = 'yh.checked.';                                  // 31 行
function checkedToday() { return safeGet(K_CHECKED + ymd()) === '1'; }   // 1349：读 …2026-10-26
function markCheckedToday(on) { safeSet(K_CHECKED + (on || ymd()), '1'); } // 1351：on=true ⇒ 写 …true
...
markCheckedToday(true);   // 4367 / 4451 两处调用
```
`true || ymd()` 短路成 `true`，写的是 `yh.checked.true`，读的是 `yh.checked.2026-10-26` ⇒ **永远读不到**，`syncCheckinButtons()` 永远走"未签到"分支。

**影响**：每个用户每天都看到"未签到、可点"，会重复点；服务端虽按日去重（同日只计一次观测），但用户不知道已签成功。这直接影响 7 天基线（`min_observations=7`）的达成体验。

**建议**：`markCheckedToday(on)` 改为 `safeSet(K_CHECKED + (typeof on === 'string' && on ? on : ymd()), '1')`；并给签到成功补一条 toast。
**验收标准**：点一次后 `#homeCheckinText` 文案＝「今日已签到」、`#btnHomeCheckin.disabled===true`、`localStorage['yh.checked.'+当天]==='1'`；刷新页面后仍为已签到。
**工作量**：L1（3 行）＋ 回归 1 条。

### P1-2 「我的」页健康分与首页不一致（66 vs 56）

**现象**（同一账号同一时刻）：
- 首页 `#idxScoreLive` = **56**；节律页 `#indexScore` = **56**（一致）；
- 我的页「今日健康指数 / 健康档案」一行 = **今日 66 分**。

**根因**（代码对照）：
- 首页/节律页：`liveDailyScore(base)` = `base + liveDayOffset()`（时段回落 ≈ −10）
- 我的页（app.js 304154）：
```js
var idx = (state.daily && state.daily.index) || null;
$('mineRhythmNote').textContent = '今日 ' + Math.round(num(idx.score)) + ' 分';   // 直接用原始 66
```
接口 `/rhythm/daily` 的 `index.score` 确实是 66（`display.score`），首页再叠"时段回落"到 56 —— **我的页漏了这一步**。

**影响**：这正是 v154 修过的同类问题（当时修的是首页 vs 节律页），现残留在「我的」页；用户会以为数据坏了。
**建议**：我的页同一处改用 `liveDailyScore(Math.round(idx.score))`，并加"15 分钟同时刷新"（v154 已有机制，挂进去即可）。
**验收标准**：同一时刻三处数字完全相同（首页＝节律＝我的），且随 15 分钟刷新同时变化。
**工作量**：L1（1 行 + 1 处刷新挂钩）。

### P1-3 音乐推荐里的"能量"恒定 152.x，与任何账号都无关 —— 个性化失效

**现象**（实测两个出生信息差异极大的账号，同一时刻）：

| 账号 | 出生 | `/vault/energy` | `/music/recommend` 的 `basis.energy` |
|---|---|---|---|
| A | 1988-07-09 08:30 丽水 | **80.1** | **152.1** |
| B | 1962-02-03 23:40 乌鲁木齐 | **212.1** | **152.1** |

- 带令牌与不带令牌，推荐能量**都是 152.3**；
- 推荐文案恒为「能量 152.x（低于 200）：先用宫音稳住中焦」，`need_recharge=true`。

**根因**：`shuzi\server\musiclib.py:256-260`
```python
member_id = getattr(ctx, 'member_id', '') or ''
energy = self.energy_api._energy_parts(member_id, hour) ...
```
该路由为可匿名（`auth_required=False`），`ctx.member_id` 取不到 ⇒ `_energy_parts('', hour)` 用默认五行权重 ⇒ 恒 152.x。

**影响**：① 所有用户被同一套"能量偏低"话术推荐（与本人无关）；② 音乐页显示 152、首页显示 80，前后不一致；③ 属"看起来个性化、实际没有"，对口碑与合规口径都不利。
**建议**：推荐路由内自行解析令牌（或在可匿名路由里把 member_id 透传进来），取不到令牌时才用匿名默认；同时把 `basis.energy` 与 `/vault/energy` 的 `index` 用同一个函数、同一时刻计算。
**验收标准**：A/B 两账号同一时刻 `recommend.basis.energy == /vault/energy.index`（±0.2 内），且两人数值不同；匿名访问仍可返回（走默认）。
**工作量**：L2（服务端 1 处 + 回归脚本 1 个）。

### P2-4 「健康商城」tab 直接跳出单页应用，并带入第三方 SDK 报错

**现象**：点底部「商城」→ `location.href = MALL_URL`（`app.js` `openMall()`），整页离开元神；回到原页只能靠系统返回。
在体检中该跳转带来的控制台报错（非元神自身代码）：
```
极光：jiguang225
获取首页提示信息失败: {message: 未登录}
获取系统消息未读数量失败: {message: 未登录}
[system] API `requireNativePlugin` is not yet implemented
加速授权页拉起成功
Error: <path> attribute d: Expected number, "M0,0 LNaN,NaN Q0,0,NaN…"   ×2
```
**影响**：App 内失去底栏与返回一致性；第三方（极光推送）在主站 H5 里初始化，浏览器环境必然报错；`NaN` 路径说明商城页有图表在无数据时画坏。
**建议**（任选，需师父定）：
1. 用 `iframe`/内嵌 WebView 承载，保留底栏与返回（改动小，但要处理跨域与登录态）；
2. 保持跳出，但在跳转前弹一句"即将进入商城，返回请按系统返回键"，并在商城页修掉 `NaN` 路径；
3. 商城独立为小程序/H5 入口，底栏去掉该项。
**验收标准**：从商城返回后仍在原 tab（或明确提示返回方式）；元神自身控制台 0 报错。

### P2-5 游客首屏就对需要登录的接口发请求（401 / 422）

实测（线上、未登录、仅打开首页）：
```
401 /api/v1/vault/energy
422 /api/v1/rhythm/daily?target_date=2026-10-26
```
页面无可见错误，但控制台两条红字；`/rhythm/daily` 是核心接口，被 422 掉说明缺参数/缺档案时返回语义不清。
**建议**：前端在未登录时不请求 `/vault/energy`（已有 `homeEnergyRow hidden` 逻辑，前置判断即可）；`/rhythm/daily` 补 `target_date` 之外的必填校验说明，或对游客返回 200 + 明确 `code`。
**验收标准**：游客首屏 Network 面板 0 个 4xx；控制台 0 条 error。

### P2-6 静态资源没有 `Cache-Control`（有 ETag，但每次都要条件请求）

实测线上头：

| 资源 | 压缩 | 线上字节 | Cache-Control |
|---|---|---|---|
| `/` | gzip | 32,095 B | **无** |
| `/app.js` | gzip | 125,484 B | **无** |
| `/style.css` | gzip | 27,944 B | **无** |
| `/version.json` | 未压缩 | 13,949 B | **无** |

**影响**：每次冷启动都要对 700 KB 级资源做一次条件请求（虽 304 不传正文，但 RTT × N）；WebView 首开体验受影响。
**建议**：带 `?v=` 的静态件发 `Cache-Control: public, max-age=31536000, immutable`；`index.html` 发 `no-cache`；`version.json` 发 `no-cache`（它是版本探测入口）。
**验收标准**：`curl -I` 三个资源各见对应头；第二次进入元神（同一 `?v=`）无网络请求正文传输。
**工作量**：L2（IIS `web.config` 一处）。

## 四、性能实测（线上真机视口）

| 指标 | 手机（4G 模拟 1.6 Mbps + CPU 4x） | 手机（本机宽带） |
|---|---|---|
| TTFB | 203 ms | 343 ms |
| FCP | 812 ms | 600 ms |
| DOMContentLoaded | 1,495 ms | 1,345 ms |
| 首屏资源 | 14 个 / 197 KB 传输 / 649 KB 解码 | 16 个 / 204 KB / 651 KB |
| 二次访问 | —（同会话）58 ms DCL | — |
| 第三方域名 | 无（全部同源，这点很好） | 无 |

> 对照：**本地** 15041（`serve.py`，无 gzip）同样 4G 模拟是 DCL 4,075 ms / FCP 1,608 ms / 659 KB —— 说明线上的压缩把弱网首屏从 4 s 级拉到 1.5 s 级，gzip 是已经吃到的红利；本地数字不代表线上。

**体积结构**（本地正本 = 线上逐字节一致，MD5 全同）：

| 文件 | 原始 | gzip 线上 |
|---|---|---|
| `index.html` | 139,029 B（26 个 screen 全内联） | 32,095 B |
| `app.js` | 444,989 B（9,232 行，单文件 IIFE） | 125,484 B |
| `style.css` | 122,213 B | 27,944 B |
| `music.js` / `energy.js` / `energy-flow.js` | 21 KB / 17 KB / 30 KB | — |

**结论**：网络层已合格；真正的成本是**单文件体量**（445 KB JS 在低端机上解析/执行）。建议（按性价比排序）：
1. 首屏只渲染 `home`，其余 25 屏改为模板懒注入（HTML 139 KB → 预计 ~40 KB）；
2. `app.js` 按域拆分（能量/音乐/家人/积分各一包，进页再取），复用 `cities-x.js` 已有的按需加载模式；
3. 关键 CSS 内联 + 其余异步（当前 CSS 阻塞首屏渲染 122 KB）。
