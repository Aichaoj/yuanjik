# 变更单 · 健康档案录入与「提前建档打分」（v2）

> 变更 id：`2026-10-08-健康档案与提前建档打分`
> 日期：2026-10-08　｜　等级：**L2（接口新增 + 数据新增；站点为 L3 但沿用已上线通道）**
> 师父指令原文：「如果用户提供或者完善相关数据比如身高体重，血压及上传病历等等，可以提前建立数字档案并打分，说明需要观察完善即可。」
> 依赖：v1（今日节律指数 `index`，正在实现）

---

## 一、意图

用户**只填生辰**时，只能给出「时相分」（出生时空 + 当日运气推算，人人都能算，区分度有限）。
用户**再补体征数据**（身高、体重、血压、心率，可选的病史自述）后，应当：

1. **提前建立数字档案**（不必等 7 次打卡）；
2. 给出**更贴合本人的分数**（时相分 + 自报体征的确定性修正）；
3. 明确告知**还需持续观察完善**（个体化基线仍需 n/7）。

## 二、范围（本期做 / 本期不做）

### 本期做（无合规门槛）
| 项 | 说明 |
|---|---|
| 结构化体征录入 | 身高 cm、体重 kg（→ BMI 自动算）、收缩压/舒张压 mmHg、静息心率 bpm；全部**可选**，填几项算几项 |
| 病史**自述文本** | 用户自己写（如"高血压 5 年，服氨氯地平"），**不做任何自动判读**，仅作为档案内容与提示 |
| 单独同意 | 体征属敏感个人信息 → 提交前必须**单独勾选**同意（不得与总协议捆绑），可随时撤回并删除该档案 |
| 档案完整度 | `archive.completeness` 0–100 + 缺失项清单，用于提示"补齐后更准" |
| 提前建档打分 | 有体征数据时给出 `score_with_vitals` 与**公开公式**；`archive_established=true` |
| 文案 | 结果页固定一句：「数字档案已建立；个体化结果仍需连续记录（n/7）」 |

### 本期**不做**（合规门槛未过，需师父裁决）
| 项 | 为什么不能现在做 | 需要什么前置 |
|---|---|---|
| **病历原件上传**（图片/PDF） | ① 病历属**敏感个人信息**（PIPL 第 28/29 条），须单独同意 + **加密存储** + 最小化 + 留存期限 + 访问审计；② 我们自己的合规设计（`方案/11`、`PIPL合规研究`）把"列级加密/密钥管理"划给**关联方加密信道**；③ 本侧**被明令不得自行实现加密/密钥管理** | 关联方加密信道接口就绪 + 出台《健康档案留存与删除策略》+ 明确暂存期与到期自动删除 + 访问审计留痕 |
| 化验单自动识别（OCR→指标） | 会引入第三方处理者（PIPL 第 21 条委托处理协议）且逼近器械边界 | 委托处理协议 + 器械边界评估 |

> **替代方案（推荐先走）**：让用户**手工填关键指标**（血压/血糖/血脂等），既拿到"提前建档打分"的收益，又完全不落敏感原件。

## 三、接口契约（新增，不改既有字段）

### `POST /api/v1/profile/health`（新增；需鉴权；幂等）
请求：
```json
{
  "height_cm": 175, "weight_kg": 70,
  "bp_systolic": 128, "bp_diastolic": 82, "resting_hr": 72,
  "history_note": "自述文本，可为空",
  "consent_sensitive": true        // 必须为 true，否则 10007（拒绝处理）
}
```
响应 `data`：
```json
{
  "archive_established": true,
  "completeness": 60,
  "filled": ["height_cm","weight_kg","bp"],
  "missing": ["resting_hr","history_note"],
  "bmi": 22.9, "bmi_band": "正常范围",
  "bp_band": "正常高值",           // 仅作区间归类，不作诊断
  "consent_sensitive": true,
  "updated_at": "2026-10-08T03:00:00Z"
}
```
- 校验：身高 80–250、体重 20–300、收缩压 60–260、舒张压 30–180、心率 30–220；越界 → `10002`（字段非法）并指明字段名
- 撤回同意：`DELETE /api/v1/profile/health`（新增）→ 删除该档案并返回 `{"deleted": true}`

### `GET /api/v1/rhythm/daily`（既有；仅**新增**字段）
```json
"archive": {
  "established": true, "completeness": 60,
  "missing": ["resting_hr"], "note": "补齐后个体化结果更准"
},
"index": {
  "...": "v1 字段保持不变",
  "score_with_vitals": 78,          // 无体征数据时为 null
  "vitals_formula": "score_with_vitals = round(score - Σ penalty_i)，penalty 见下",
  "vitals_factors": [{"item":"bp","value":"128/82","band":"正常高值","penalty":4}]
}
```
**修正公式（必须公开、可复算，不许拍脑袋）**：
```
penalty_bmi   : BMI<18.5 或 24–27.9 → 3；BMI≥28 → 6；否则 0
penalty_bp    : 正常高值 → 4；1 级及以上 → 8；偏低 → 3；否则 0
penalty_hr    : 静息心率 >100 或 <50 → 4；90–100 → 2；否则 0
score_with_vitals = clamp(round(score - Σ penalty), 0, 100)
```
> 全部为**区间归类与加减分**，不做诊断、不做疾病判定；文案不得出现疾病名，只能写区间标签（如"正常高值"）。

## 四、验收标准（可验证，逐条自检）

| # | 验收标准 |
|---|---|
| 1 | `POST /api/v1/profile/health` 带 `consent_sensitive=true` 且合法 → 200，`data.archive_established=true` |
| 2 | **不带** `consent_sensitive`（或 false）→ 拒绝：`code=10007` 且 HTTP 4xx，档案**不落库** |
| 3 | 越界值（如身高 400）→ `code=10002` 且 `detail.field` 指明字段名 |
| 4 | 提交后 `GET daily` 的 `data.archive.completeness` **>0**，且 `index.score_with_vitals` **非空** |
| 5 | 同输入两次调用 `score_with_vitals` **逐位一致** |
| 6 | 只填身高体重 vs 再补血压 → 两者 `score_with_vitals` **不同**（血压 penalty 生效） |
| 7 | `DELETE /api/v1/profile/health` → 再取 daily，`archive.established=false`、`score_with_vitals=null` |
| 8 | 未填任何体征的新用户：`index.score` 仍有值（v1 行为不回归），`score_with_vitals=null` |
| 9 | 返回文本过合规护栏：**无**诊断/治疗/疾病名；免责声明与 AI 标识仍在 |
| 10 | 前端 430×932：① 存在"完善健康档案"入口；② 提交后首屏分数卡出现"含自报体征"标识与完整度进度；③ 撤回同意后可一键删除；④ 无 JS 报错 |
| 11 | 「数字档案已建立；个体化结果仍需连续记录（n/7）」这句提示在结果页**可见** |
