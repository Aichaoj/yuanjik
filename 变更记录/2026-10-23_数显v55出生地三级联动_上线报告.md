## 一、做了什么

出生地由「一个 705 项的大下拉」升级为 **省 → 市 → 区县** 三级：

| 级 | 内容 | 条数 |
|---|---|---|
| 省 | 23 省 / 5 自治区 / 4 直辖市 / 港澳台 | 34 |
| 市 | 地级市 · 自治州 · 盟 · 地区 · 县级市 | 705 |
| 区县 | 区 / 县 / 自治县 / 旗 / 林区（**选填**） | **2786** |

- 建档屏、家人表单两处都改（`#inProvince/#inCity/#inCounty`、`#famProvince/#famCity/#famCounty`）；
- 区县不选 = 用市坐标（老数据、县级市下属无区县，都走这条）；
- 家人「编辑」按坐标反查：**先认区县**（0.05°≈5.5 km），再退到市，都认不出才进「手动输入经纬度」。

## 二、为什么区县数据要单独一个文件

线上 IIS **没开 gzip**（实测 `app.js` 368 KB 原样下发）。若把 2786 条区县塞进 `app.js`，会变 570 KB，
**所有用户**（包括从不填出生地的）首屏都要多下 200 KB。

故新增 `web/cities-x.js`（**77 KB**），只在打开建档 / 家人表单时按需加载；首屏体积一分钱没涨（app.js 368 → 377 KB，只多了三级联动逻辑）。

文件格式（省体积）：
```
浙江省|杭州|桐庐县:119.691,29.794;富阳区:119.96,30.049;…
```

## 三、数据来源与口径

| 项 | 值 |
|---|---|
| 源 | 彩云《全国行政区经纬度对照表》`Adcode_release_2021-11-30`（3557 条县级以上，UTF-8） |
| 生成脚本 | `_toolchain\cities\gen_counties.py`（区县）＋ `gen_cities.py`（省市，v54 已有） |
| 坐标精度 | 区县 3 位小数（≈110 m）；1° 经度 ≈ 4 分钟真太阳时 ⇒ 精度绰绰有余 |
| 可复跑 | 是（脚本 + 源文件都在 `_toolchain\cities\`，换新版本表即可重生成） |

## 六、未验证项与风险

1. **真机弱网未验**：我这边是 390×844 无头 Chromium；`cities-x.js` 77 KB 在 3G 下的加载体感需师父真机点一次。
2. **区县加载失败时的降级**：`cities-x.js` 取不到时，区县下拉会停在「不选（用市坐标）」，市级选择与保存不受影响（已设计，但未造假网络场景实测）。
3. **直辖市范围**：北京/上海/天津/重庆 的「市」只有 1 项，区县里列的是各区（如 东城区），符合预期但需师父确认口径。
4. **数据表版本**：表为 2021-11-30 版，个别改名（如「漠河县」现为漠河市）未覆盖；这类只有县级市改制的少数地区。
5. **`app.js` 377 KB**（+9 KB）：仍是未压缩下发，后续若做 IIS gzip，可一并降到 ~90 KB。
