## 一、第 1 件事：为什么「签到好几天还是 1/7」

### 1.1 先取证（线上真实数据，只读）

通过既有静默通道跑只读 SQL（只 SELECT，不写业务表）：

| 项 | 实测 |
|---|---|
| 师父会员号 | `mbr_736a705e6074342f`（账号 `acc_55e9bfcfc15bc98a`，189-****-8241） |
| `checkin` 表签到天数 | **11 天**（2026-10-10 → 2026-10-24，按日一行） |
| `baseline.observation_count` | **1** |
| 该行 `s_ref` | 12 通道全 = 0.2（= 首次观测的默认分量） |
| 该行 `updated_at` | 2026-10-24T14:28:27（= 当天签到时刻） |
| 对照会员 `mbr_f2a2af3f…` | 3 天签到 → 3 ✓（说明累加逻辑本身是好的） |

⇒ **不是签到没记上**（11 条都在），是**基线里那个计数器被重置回了 1**：每次签到都走了「首次观测」分支，
于是永远停在 1/7。属于「计数漂移」，且只有这一位会员中招。

### 1.2 复现与定位

- 本机隔离库（临时 state.db）连续 3 天签到：**1 / 2 / 3**，重启后仍在库里 ⇒ 逻辑与持久化都正常；
- 线上服务进程自 10-23 12:27 起未重启（PID 36904），排除"进程内内存丢了"；
- `baseline` 表唯一的删除入口是 `BaselineService.reset()`（只有"更正出生信息 / 用户主动重置"两处），
  但该会员 `profile.updated_at` = 10-23T14:07:33，10-24 无建档提交 ⇒ 排除"出生地更正导致的重置"；
- **结论（口径：已核实的现象 + 未完全定因的机制）**：计数会被重置/漂移，但触发点未能在只读数据里坐实。
  因此修法不赌"哪一种触发"，改成**让计数以签到表为唯一事实来源自动校准**。

### 1.3 修法（`server/serve.py`，只加不改）

新增 `PersistentApiV1._heal_baseline_count(member_id)`：

- 取 `checkin` 表真实签到天数 `days`（按日一行，只增不减）；
- `days > observation_count` ⇒ 把计数补到 `days`（**只升不降**，从不把已建立的进度压回去）；
- 基线行整行缺失时，用历史观测值按同一 EWMA 参数（`BASELINE_ALPHA=0.10`）**重放**重建 `s_ref`，
  而不是从 0.2 重新开始；
- 挂载点：`checkin`（签到后）、`daily`（读节律时）、`me`（读我的）——老数据不必等到下次签到自己纠正。

合规边界：不改任何接口路径与响应形状；`reset()` 的契约语义（更正出生信息 → 基线失效）保留，
只是"进度"这一显示口径按真实签到天数自校准。

**加固（同日 14:57，部署迭代 v61）**：自愈是"读路径上的修数据"，整个函数体外层再包一层 `try/except`，
任何异常只写一行日志、**不冒泡成 500**，保证"修不好也不影响正常读页面"。
v61 回执：`serve.py 73,633 B match=True`、`CRIT_FAILURES=0`、`EXIT=0`、`SERVICE=Running`。

## 七、教训与立规

1. **"计数"不能当事实，明细表才是事实**——凡是"累计 N 次/连续 N 天"的展示值，
   必须以明细表（按日一行）为源，展示值只做缓存；否则一次重置就永久说谎。已写入 `_智能体\facts.md`。
2. **诊断先拿线上真值，再谈代码**：本次前半小时的怀疑（缓存/时区/会话）全被数据否掉，
   一份只读 SQL 抵过十次猜测。
3. **整行 upsert 的接口不能半字段调用**：`healthscore_save` 会抹掉未传字段，
   必须"先读后合并再写"——这条要进 S3 角色的禁区。
