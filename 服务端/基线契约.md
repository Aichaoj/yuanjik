# 个体基线契约（Baseline Contract）

> 制定日期：2026-10-06
> 效力：本文件是**个体基线（S_ref）生命周期的唯一口径源**。`BaselineService` 的实现与测试以本文件为准。
> 起因：专家组审核软件工程阻断-4——`update_baseline()` 写了但**没有任何调用方**，`compute_offset()` 在 `baseline=None` 时回落全 0。
> 于是"**只与自己比**"（`rules.py` OF-001，本体系与竞品的根本区别）**在代码里并不存在**。服务端若照现状开工，必然先写出一套错假设。

---

## 一、基线的定义

`S_ref` 是**目标个体自身在平稳状态下的十二通道状态量值**，单位与 `S(t)` 一致，维度 12（肝/胆/心/小肠/脾/胃/肺/大肠/肾/膀胱/心包/三焦）。

`Δ(t) = S(t) − S_ref` 是**个体内纵向对照**的结果。**全程不做跨个体比较**（OF-001）。

## 二、生命周期（五条，必须逐条实现）

### 2.1 初始化

| 阶段 | `observation_count` | `S_ref` | 对外输出 |
|---|---|---|---|
| **未建立** | 0 ≤ n < 7 | 首次观测值（n=0 时）或滚动值 | 只输出 Δ 与"基线建立中（n/7）"，**不出观察等级、不出关注通道、不出策略取向** |
| **已建立** | n ≥ 7 | EWMA 滚动值 | 完整输出 |

**为什么是 7 次**：`申报/专利/专利2` 权利要求 6 已将此写为从属权利要求，`方案/07` 的考评方案亦以"基线稳定"为前提。**代码此前未实现，现已实现**（`offset_layer.OffsetResult.baseline_established`）。

**为什么要"未建立不出等级"**：基线为 0 时，`Δ` 等于**绝对强度**；而 `0.18 / 0.35 / 0.60` 这套阈值是为**偏移量**标定的。两者量纲不同，等级没有意义。

### 2.2 一次「观测」的定义

**一个自然日内，取该日全部可用观测的均值，记为一次观测。**

- 观测来源（按优先级，同类取均值）：用户打卡记录、行为事件推算值、设备分量（有则用）
- 一日多次 → 先日内聚合为一次，再进 EWMA。**不得逐条进 EWMA**（否则活跃用户基线被过度拉动）
- 一日零观测 → **该日不产生观测，`observation_count` 不增**

> ★ **这条是防"勤奋惩罚"的关键**：若不按日聚合，一天记 5 条的用户与一天记 1 条的用户，基线更新频率差 5 倍。

### 2.3 EWMA 更新

```
S_ref ← α · S_obs + (1 − α) · S_ref
```

- `α = 0.10`（`offset_layer.BASELINE_ALPHA`，对应规则 OF-004）
- **α 变更属于规则版本变更** → 必须升 `RULE_VERSION`，且**不重算历史 Δ**（见 2.5）

### 2.4 停打卡与恢复

| 情况 | 处理 |
|---|---|
| 连续 **14 天**无观测 | 标记 `stale`，对外提示"基线可能已漂移，建议重新记录" |
| 连续 **60 天**无观测 | **不重置基线**，但把 `observation_count` 降到 7（刚够建立），使 Δ 恢复敏感 |
| 用户**主动重置**基线 | 清空 `S_ref`，`observation_count = 0`，回到未建立态；**已产生的历史 Δ 不删除** |

> **不自动重置的理由**：基线的价值在长期稳定；自动重置会让老用户"越用越像新用户"，与产品承诺相反。

### 2.5 与规则版本的关系

- `S_ref` **随 `rule_version` 存储**。规则升级后，**旧版本基线与旧版本 Δ 一并保留**，不重算、不覆盖
- 规则升级后首次读取：用旧基线按**新版本**继续更新（因为 `S_ref` 是"个体观测的统计量"，与规则版本无关）；
  但**历史 Δ 保持旧版本**，响应中标注其 `rule_version`
- **禁止**：因 `rule_version` 变更而清空用户基线

### 2.6 与更正生辰的关系

用户更正出生信息 → `S(t)` 全变 → **旧基线失效**。

处理：**清空基线，回到未建立态**，并写 `audit` 日志。这是唯一允许清空基线的自动场景。

## 三、存储

| 字段 | 类型 | 说明 |
|---|---|---|
| `member_id` | uuid | 主体 |
| `rule_version` | text | 写入时的规则版本 |
| `s_ref` | jsonb | 12 通道基线值 |
| `observation_count` | int | 累计观测次数（按日聚合后） |
| `last_observed_on` | date | 最近一次观测日期（用于停打卡判定） |
| `established` | bool | 派生列，`observation_count >= 7` |
| `updated_at` | timestamptz | — |

对应 `schema_v1.sql` 的 `rhythm.baseline`（表已存在，带 `rule_version` 列）。

## 四、接口（`BaselineService`）

```python
class BaselineService:
    def get(self, member_id) -> Baseline | None: ...
    def record(self, member_id, observed: dict[str, float], on: date) -> Baseline: ...
        """记录一次【按日聚合后】的观测；内部处理 EWMA 与计数"""
    def reset(self, member_id, reason: str) -> None: ...
    def state(self, member_id) -> BaselineState: ...   # established / progress / stale
```
