## 一、统一响应结构

### 1.1 成功

```json
{
  "code": 0,
  "message": "ok",
  "data": { },
  "trace_id": "01J8Z6M3KX9Q0F2N7P4R5T6V8W",
  "rule_version": "TYH-RULES-1.0.0"
}
```

### 1.2 失败

```json
{
  "code": 30000,
  "message": "试用已结束",
  "data": null,
  "detail": { "trial_ended_on": "2026-10-09" },
  "trace_id": "01J8Z6M3KX9Q0F2N7P4R5T6V8W"
}
```

**规则**

| # | 规则 |
|---|---|
| 1 | HTTP 状态码只表达传输层语义；**业务结果一律看 `code`**（避免 200 里藏业务错误、或 4xx/5xx 混用） |
| 2 | `code = 0` 表示成功，非 0 见 `app/errors.py` 分段表 |
| 3 | `trace_id` 每条响应必带，与日志同源 |
| 4 | `detail` 只放**结构化字段**，不得放可直接渲染给用户的文案（文案由前端按 `code` 取） |
| 5 | 涉及算法结论的响应必带 `rule_version` 与 `param_hash` |
| 6 | 涉及 AI 生成内容的响应必带 `ai_generated` 与 `disclaimer` |

### 1.3 HTTP 状态码映射

| code 段 | HTTP |
|---|---|
| 0 | 200 |
| 1xxxx | 400 |
| 2xxxx | 401（20003 冲突为 409） |
| 3xxxx | 402 |
| 4xxxx | 429 |
| 5xxxx / 6xxxx | 422 |
| 7xxxx | 403（70004 危机转介为 200，是流程非错误） |
| 9xxxx | 500 |

## 二、鉴权

### 2.1 ★ 决策：不透明令牌（opaque token）+ 服务端会话，**不用 JWT**

| 方案 | 撤销时延 | 可举证性 | 结论 |
|---|---|---|---|
| JWT（自包含） | 有 TTL 窗口，需黑名单补救 | 弱（无法证明"此刻已失效"） | ❌ |
| **不透明令牌 + 服务端会话** | **即时** | **强（有会话表可查）** | ✅ **采用** |

**理由**：本产品有两处**必须即时生效**的撤销场景——
① 用户撤回敏感个人信息同意（PIPL 第 15 条）；② 用户注销或发现账号异常。
JWT 的"自然过期"无法满足"即时停止处理"，而会话表能直接给出撤销时间戳作为举证。

### 2.2 令牌

| 项 | 值 | 说明 |
|---|---|---|
| `access_token` | 不透明随机串（32 字节，URL-safe） | **TTL 15 分钟** |
| `refresh_token` | 不透明随机串（32 字节） | **TTL 30 天**，**单次使用**（刷新即轮换） |
| 存储 | Redis：`sess:access:{token}` → `{account_id, member_id, device_id, issued_at}`<br>`sess:refresh:{token}` → 同上 | 生产用 Redis；开发用内存实现 |
| 传输 | `Authorization: Bearer <access_token>` | |
| 绑定 | 令牌绑定 `device_id`；换设备需重新登录 | |

**刷新即轮换（refresh token rotation）**：刷新时作废旧 refresh_token 并签发新的。
**重放检测**：若已作废的 refresh_token 被再次使用 → 判定为令牌泄露 → **吊销该账号全部会话**并记录安全事件。

### 2.3 登录链路（微信小程序）

```
① 前端 wx.login() → code
② POST /v1/auth/login/code  { code, device_id, device_info }
③ 服务端调微信 code2session → { openid, unionid?, session_key }
④ 身份归一（见 2.4）→ 得到或创建 account
⑤ 签发 access + refresh
⑥ 返回 { access_token, refresh_token, expires_in, account_id, member_id,
         profile_completed, consent_status }
```

**`session_key` 处理**：仅用于当次解密（如获取手机号），**不落库、不落日志**。

### 2.4 ★ 身份归一（unionid 合并规则）

**优先级**：`unionid` > `手机号` > `openid(小程序)`

| 场景 | 处理 |
|---|---|
| 有 unionid，且已存在同 unionid 的 account | 直接登录该 account |
| 有 unionid，无 account | 新建 account，写入 unionid |
| 无 unionid，有手机号且已存在同手机号 account | 登录该 account，**补写 unionid** |
| 无 unionid，无手机号 | 按 openid 新建 account（**不写 unionid**，留待后续补全） |
| 已有 openid 账号 A，新登录带来 unionid 且命中账号 B | **合并 A → B**，见 2.5 |

### 2.5 账号合并（不可逆，必须留痕）

合并规则：
1. **主账号**＝较早创建的账号（保证 member_id 稳定，避免历史数据归属变化）
2. 从账号的 `account` 行标记 `merged_into = 主账号`，**不物理删除**
3. 从账号下全部业务数据的 `account_id` 改写为主账号，**写入 `audit.account_merge_log`**（含合并前后 ID、触发原因、时间戳）
4. 若两账号均有付费订阅 → **取权益较高者**，剩余期限**不叠加**（避免刷单套利）；差额按退款规则处理
5. 若两账号均有心理测评记录 → **全部保留**，不做去重（量表记录不可合并）

### 2.6 多设备与并发登录

| 项 | 规则 |
|---|---|
| 允许同时在线设备数 | **5 台** |
| 超出时 | 踢掉**最早登录**的设备，并给该设备推"你的账号在另一台设备登录" |
| 家庭共用设备 | 属正常场景（`方案/00` 支持一号管 8 位家人）→ **不按设备指纹封禁** |
| 用户主动踢下线 | `POST /v1/auth/sessions/revoke-all`（≤2 步，与订阅取消同标准） |
| 注销 | `POST /v1/auth/logout` 吊销当前会话；不删账号 |

### 2.7 鉴权失败

| 情形 | code |
|---|---|
| 无令牌 / 格式错 | 20000 |
| access 过期 | 20001（前端据此走 refresh） |
| 令牌被吊销（撤回同意、注销、泄露） | 20002 |
| 设备 ID 与令牌不匹配 | 20004 |
| 超设备数（并发登录冲突） | 20003 |

## 三、限流

**算法**：Redis 令牌桶（Lua 原子），键 `rl:{scope}:{id}`。

| scope | id | 容量 | 补充速率 | 命中响应 |
|---|---|---|---|---|
| `login` | IP | 10 | 10/小时 | 429 / 40000 |
| `sms` | 手机号 | 5 | 5/小时 | 429 / 40000 |
| `api` | account_id | 120 | 120/分钟 | 429 / 40000 |
| `api_anon` | IP | 60 | 60/分钟 | 429 / 40000 |
| `ai` | account_id | 20 | 20/小时 | 429 / 40002 |
| `export` | account_id | 3 | 3/天 | 429 / 40000 |
| `guardrail` | api_key | 600 | 600/分钟 | 429 / 40000 |

**规则**
- 短信类限流**必须**在发送前判定，且**同手机号 + 同 IP 双维度**（防短信轰炸）
- 响应头返回 `X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset`
- 命中限流**要写审计**（同一 id 连续命中 ≥10 次触发风控观察，不自动封禁）

## 四、幂等

**写接口必须携带 `Idempotency-Key` 请求头**（客户端生成的 UUID）。

| 项 | 规则 |
|---|---|
| 存储 | `ops.idempotency_key` 表（`schema_v1.sql` 已有），键 = `(account_id, key)` |
| 有效期 | 24 小时 |
| 行为 | 同键重复请求 → 返回**首次的响应体**，并置 `code=0`；不重复执行业务 |
| 冲突 | 同键但请求体哈希不同 → `10003`（幂等键重放） |
| 必带接口 | 建档、打卡、行为录入、测评提交、订阅下单、邀请领取 |

## 五、分页

**游标分页（cursor-based），不用 offset。**

```
GET /v1/rhythm/history?limit=30&cursor=<opaque>
→ { "items": [...], "next_cursor": "...", "has_more": true }
```

**理由**：节律历史按时间倒序、数据持续增长，offset 分页在深翻页时性能与一致性都会出问题。

`limit` 上限 **100**，默认 30。

## 六、版本策略

| 项 | 规则 |
|---|---|
| 路径版本 | `/v1/...`；不兼容变更升 `/v2/` |
| 兼容变更 | 只增字段、不删字段、不改字段语义 |
| `rule_version` | **不是 API 版本**。规则升级不改路径；响应中如实返回产生该结果的 `rule_version` |
| 历史结果 | **不重算**。按 `rule_version` 冻结存储，需要新版就生成新行（见《基线契约》§2.5） |
| 停用 | 旧版本路径至少保留 **12 个月**，停用前 90 天公告 |

## 七、请求上下文

每条请求生成 `RequestContext`：`trace_id` / `account_id` / `member_id` / `device_id` / `client_ip` / `started_at`。
**所有日志与审计记录必须带 `trace_id`**——这是"能否定位一次事故"的分水岭。
